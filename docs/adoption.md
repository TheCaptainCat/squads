# Adopting squads in an existing project

This guide covers bringing an existing project under `sq` management — whether it already has a
squads-shaped folder, or just a pile of issue/spec markdown you want to migrate while **preserving
the original dates**.

The key tool for history is the global **`--at <when>`** option: every time-based command
(`create`, `status`, `update`, `body`, `comment`, `add-story`/`add-subtask`, `ref add`, …) records
its timestamps from `--at` instead of the wall clock. A human or an LLM driving the migration can
therefore forge the historical dates so the imported history looks real.

```bash
sq --at 2024-01-15            create task "Fix login" --author tech-lead   # created_at = that date
sq --at 2024-01-15T09:30:00Z  task 2 status InProgress
```
Every `create` needs `--author`, the slug of a registered role (or `op-<slug>` for a human
operator). `--at` accepts an ISO-8601 date or datetime (a bare date is midnight; naïve values are
UTC). It is a **global** option, so it goes *before* the subcommand and applies to that one
invocation.

## 1. Install and scaffold

```bash
uv tool install squads          # or: uvx --from squads sq …
cd your-project
sq adopt                        # non-destructive: see below
```

**`sq adopt`** is the idempotent cousin of `sq init`:

- creates `.squads.toml` if missing (keeps it otherwise);
- ensures the squad folder + per-type subfolders and the `.claude/` scaffolding;
- **imports** any squads-native `.md` files already present (rebuilds the index + the global
  counter from their frontmatter — same engine as `sq repair`, which means it also **rewrites**
  those files where they carry content squads does not store; see
  [What `sq repair` writes](#what-sq-repair-writes));
- activates the bundled roles it doesn't already have.

Run it as often as you like; it never clobbers a body you wrote. What an index rebuild does rewrite
is described under [What `sq repair` writes](#what-sq-repair-writes). Use `--squad-dir`, `--roles`,
`--no-claude` exactly like `init`.

Once the squad exists, consider opening it with the optional interview — see
[agents.md](agents.md#opening-a-new-squad-the-interview).

If your existing files **already** follow the squads layout (type subfolders, `PREFIX-NNNNNN-*.md`
filenames, sq frontmatter), `sq adopt` is all you need — it indexes them in place. If not, convert
them (next section).

### Pre-existing CLAUDE.md and .claude files

If your project already has a hand-written `CLAUDE.md` or `.claude/` directory, `sq adopt` (or
`sq init`) handles the collision non-destructively:

**The managed section is inserted at the top of CLAUDE.md.** If `CLAUDE.md` already exists
with hand-written content, the squads-managed operating-model section (the `<!-- squads:start
-->…<!-- squads:end -->` block) is prepended, and the pre-existing prose survives intact below
it. You'll see a warning:

```
warning: CLAUDE.md had pre-existing hand-written content with no squads markers;
the managed section was inserted at the top — review it for possible contradiction
with that content.
```

The managed section is regenerated by every `sq sync`, so any hand-edits inside its markers are
lost on the next sync. To preserve your operating-model guidance:
- **Move hand-written prose outside the markers** (below the `<!-- squads:end -->` line), or
- **Fold it into the managed section** before the next sync (edit the template instead of the
  rendered file).

Read both blocks to ensure they agree — if your old CLAUDE.md delegates differently than the
squads-generated one, adjust your workflow or override the templates (see `docs/overrides.md`).

**Orphan .claude files are listed as warnings, never deleted.** Pre-existing `.claude/agents/*.md`
pointer files or `.claude/skills/<name>/` directories that don't match any activated role or
custom skill are left in place. You'll see:

```
warning: candidate orphan (not managed by this squad, never auto-deleted): .claude/agents/some-old-role.md
```

This means squads found a `.claude/` file it doesn't generate — perhaps from a previous manual
setup or a custom role you've since renamed. To clean it up:
1. **Verify it's safe.** Check the file to confirm it's not something you want to keep.
2. **Back it up if needed** (before running `sq sync` again).
3. **Remove it by hand** (`rm .claude/agents/some-old-role.md` or `rm -rf .claude/skills/old-skill/`).

Squads never touches these files — you are always in control.

### The working language

A squad works in one language, set by `working_language` in `.squads.toml`:

```toml
working_language = "fr"
```

Agents then use two languages, and only one of them is configured:

- **The working language** is for everything that goes through `sq` (item titles, bodies,
  sub-entity text, comments) and for all communication between agents (briefs, handbacks,
  `@mention` comments).
- **The conversation language** is the one a human writes in. Agents reply to each person in that
  person's language, message by message; it is never configured.

The value is a BCP 47 tag, for example:

| Tag | Rendered as |
|-----|-------------|
| `en` | English (`en`) |
| `fr` | French (`fr`) |
| `de` | German (`de`) |
| `pt-BR` | Portuguese (Brazil) (`pt-BR`) |
| `zh-Hant-TW` | Chinese (Traditional, Taiwan) (`zh-Hant-TW`) |

`sq init`, and `sq adopt` when it creates `.squads.toml`, write `working_language = "en"`. An adopt
over an existing `.squads.toml` leaves that file as it is, so a squad without the key works in
English, silently, until you add it. Run `sq sync` after setting or changing the key: it refreshes
the rule in the managed `CLAUDE.md` and `AGENTS.md` sections, and the `squads` skill shows it the
next time it is read. A value squads does not recognise as a language tag (`fr_FR`, say) prints a
warning on every command and in `sq check`, and English applies until you fix it. The full rule is
in [stability.md § "Working language in `.squads.toml`"](stability.md#working-language-in-squadstoml).

This setting is not the language of the `sq` CLI's own output, which is a separate matter.

## 2. Convert legacy documents (preserving history, one-by-one)

For each legacy artifact (an old ticket, spec, ADR, …):

1. **Recreate it as a squads item at its original date.** `create` prints the new file path:
   ```bash
   sq --at 2024-01-15 create feature "User authentication" --parent EPIC-1 --author product-owner
   # → created FEAT-7 → squads/features/FEAT-000007-user-authentication.md
   ```
2. **Move the legacy content into the body** with `sq <type> <n> body` (`--file` is easiest for
   existing prose); for features, scaffold the user stories; for tasks, the subtasks:
   ```bash
   sq --at 2024-01-15 feature 7 body --file legacy-feature.md
   sq --at 2024-01-15 feature 7 add-story "As a user, I want to log in" -m "Acceptance: …"
   sq --at 2024-01-16 task 8 add-subtask "Validate token" --story US1
   ```
3. **Replay the status history** in order, each at its real date:
   ```bash
   sq --at 2024-01-16 task 8 status InProgress
   sq --at 2024-01-20 task 8 status Done
   ```
   (Only the final status persists in the index; the dated discussion entries below are what give
   you the timeline.)
4. **Re-create comments / hand-offs** as dated discussion entries, attributed to the right agent:
   ```bash
   sq --at 2024-01-17T14:00:00Z task 8 comment --as reviewer -m "LGTM, ship it"
   ```
5. **Re-link relationships** (parent, bug/review refs):
   ```bash
   sq --at 2024-01-15 task 8 ref add BUG-9 --kind fixes
   ```

Work in chronological order so each `updated_at` reflects the last real activity.

## 3. Bulk import from JSONL

For large migrations or programmatic conversions, use `sq import` to load a JSONL event stream
in one batch. Each line is a JSON object describing one operation (create an item, set its status,
add a comment, …). The tool validates every event's type, status vocabulary, and actor
registration, collecting **all** problems up front — only a fully clean file is applied, in one
transaction.

```bash
sq import history.jsonl                                  # apply events as-is
sq --at 2024-01-15T09:00:00Z import history.jsonl        # set file-level default timestamp
sq import history.jsonl --as manager --dry-run           # validate without writing
```

For a large or complex file, **always use `--dry-run` first** to see the plan:

```bash
sq import history.jsonl --dry-run
# → lists the projected item allocations and any validation errors
```

**Validation failures write nothing.** If the file has any error (bad JSON, unknown status,
missing parent, …), the whole file is rejected with a line-numbered error report. Fix the file
and re-run — there is nothing to recover because nothing was written.

**A refusal while the file is applied writes nothing either.** Some refusals come only once an
event is applied, such as a `body` event without `"force": true` on an item whose body is already
written. The import then stops with that error and leaves every item file and the index as they
were: no item is created, written or renamed.

**Recovering from a crash while the files are written.** An import writes its item files at the
end, then commits the index. If the process is killed, or the disk fails, between those writes,
some item files can be on disk with the index uncommitted, leaving the index out of sync. If that
happens:

1. Run `sq repair` immediately:
   ```bash
   sq repair     # reconciles the index to whatever files exist on disk
   ```
   `sq repair` also **rewrites content**, not just the index — see
   [What `sq repair` writes](#what-sq-repair-writes) below. On a corpus carrying regions squads
   does not store, that content diff arrives on top of the half-written import you are trying
   to inspect, and the two cannot be told apart afterwards. Commit or stash the partial import
   first, so the next step's `git diff` shows the repair's work on its own.
2. Inspect what landed. Use `sq tree` or `sq list` to see which items made it:
   ```bash
   sq tree       # view the current state of all items
   ```
3. **Do not re-run the same import file.** This version of squads has no idempotency — a
   re-run allocates fresh IDs and **duplicates every item**. Instead:
   - Compare the file to what landed and manually add the missing items (`sq create`, one at a
     time).
   - Or start fresh by renumbering and skipping events you've already created.

The `--dry-run` option is your guard against an accidental second run — always validate before
applying to a production squad.

### Event reference

Each line is one JSON object, and its `op` key names the event. A blank line is skipped. A key the
event does not declare is refused (`create.id: Extra inputs are not permitted`), so a typo is an
issue rather than a value silently dropped.

**Who and when.** `as` is the slug of a registered role or operator, who performs the event and,
on a `create`, authors the item. `at` is an ISO 8601 timestamp. An event that gives neither keeps
the previous event's value; the first event falls back to `sq import --as` and to the global
`sq --at` (or the current time). An event with no actor from any of these is refused
(`no actor: missing 'as'`).

**Naming what the file creates.** The ids a `create` will get are unknown when you write the file,
so a `create` or an `add-*` event can declare a `handle`, a name of your own. A later event names
the item, or the sub-entity, by that handle wherever it takes an id: `target`, `parent`, `to`,
`refs`, `deferred_to`, and the sub-entity selectors `local`, `story`, `subtask` and `finding`. A
token that is not a handle is read as an id (`TASK-12`) or a local id (`ST1`). `--dry-run` prints
the id each handle will get.

**Values are checked as on the CLI.** A `status` must be one the type's lifecycle declares, and a
move the lifecycle does not allow needs `"force": true`; a `create` sets its `status` directly. A
`fields` map takes field codes to collection codes (`{"priority": "high"}`); a field a `create`
leaves out stores its declared default. `kind` is a sub-entity kind the workflow declares
(`story`, `subtask` and `finding` in the bundled one). A title must not be blank on an item; a
sub-entity's title is optional.

| `op` | Required | Optional | What it does |
|------|----------|----------|--------------|
| `create` | `type`, `title` | `description`, `parent`, `labels`, `refs`, `assignee`, `fields`, `status`, `slug`, `body`, `handle`, `at`, `as` | Creates an item. `refs` entries are `"ID"` or `"ID:kind"`; `slug` sets the file name's slug. |
| `status` | `target`, `status` | `force`, `at`, `as` | Moves an item to a status. |
| `body` | `target`, `body` | `append`, `force`, `at`, `as` | Writes the item's body. Replacing a written body needs `force`; `append` adds to it. |
| `comment` | `target`, and `message` or `messages` | `story`, `subtask`, `finding`, `sub`, `at`, `as` | Adds one discussion entry, one bullet per message. A selector puts it on a sub-entity's discussion: `story`, `subtask` or `finding` names the local id, `sub` is `[kind, local]`. Give at most one. |
| `ref` | `target`, `to` | `kind`, `at`, `as` | Adds a ref from `target` to `to`. Without `kind`, the workflow's default kind. |
| `add-sub` | `target`, `kind` | `title`, `story`, `fields`, `assignee`, `status`, `deferred_to`, `body`, `handle`, `at`, `as` | Adds a sub-entity of any kind. `story` maps a subtask to a story of the task's parent feature. |
| `add-story` | `target` | `title`, `assignee`, `status`, `body`, `handle`, `at`, `as` | `add-sub` with `kind` `story`. |
| `add-subtask` | `target` | `title`, `story`, `assignee`, `status`, `body`, `handle`, `at`, `as` | `add-sub` with `kind` `subtask`. |
| `add-finding` | `target` | `title`, `severity`, `assignee`, `status`, `deferred_to`, `body`, `handle`, `at`, `as` | `add-sub` with `kind` `finding`; `severity` is the finding's severity code. |
| `sub-status` | `target`, `kind`, `local`, `status` | `deferred_to`, `force`, `at`, `as` | Moves a sub-entity to a status. |
| `sub-body` | `target`, `kind`, `local`, `body` | `append`, `force`, `at`, `as` | Writes a sub-entity's body, with the same `append` and `force` rules as `body`. |
| `assign` | `target` | `assignee`, `kind`, `local`, `at`, `as` | Sets the item's assignee, or a sub-entity's with `kind` and `local`. Without `assignee`, removes it. |
| `update` | `target`, and at least one change | `title`, `description`, `assignee`, `clear_assignee`, `add_labels`, `rm_labels`, `parent`, `clear_parent`, `status`, `force`, `fields`, `unset_fields`, `at`, `as` | Changes an item's metadata, like `sq <type> <n> update`. `fields` sets field values and `unset_fields` removes them by code. |

A status whose role declares `deferred = true` (the bundled finding's `Deferred`) needs
`deferred_to`, the item that carries the work: an `add-sub`, `add-finding` or `sub-status` event
that reaches it without one is refused.

An `update` event that names no change is refused (`nothing to update: the event names no field`).
`"clear_assignee": true` removes the assignee; an empty `assignee`, or `assignee` together with
`clear_assignee`, is refused. Clearing an assignee the item does not have writes nothing.

```json
{"op": "update", "target": "TASK-13", "clear_assignee": true}
```

## 4. Validate

```bash
sq check        # markers, dangling parents/refs, invalid status, frontmatter↔index drift
sq tree         # eyeball the imported hierarchy
sq repair       # rebuild the index from frontmatter if anything looks off
```

`sq repair` and `sq check` read timestamps straight from the frontmatter, so the dates you forged
with `--at` are preserved across rebuilds.

### What `sq repair` writes

`sq repair` rebuilds the index, and on the same pass it **rewrites item files**. It removes what
squads computes on every read rather than stores:

- the sub-entity roll-up table and each sub-entity block's badge line, from any item file that
  carries them;
- the keys a role item mirrored from its definition (`full_name`, `mission`, `responsibilities`,
  `agreements`, `color`, `can_spawn`, `skills`, `is_dev`). A role keeps its `title` (its name),
  `slug` and `description`, its default-role designation, a developer role's `model` and `tech`,
  and any other key.

It also canonicalises any legacy ref encoding it finds, and fills an **empty** body region on a
role or a generated skill (`squads`, `greeting`, `sq-memory`, `sq-<type>`) with the view tag
that `sq role <slug> show` / `sq skill <slug> show` render the definition into. That definition
comes from the role catalog, the bundled templates and your own overrides, so make sure a role you
defined yourself has its `.overrides/roles/<slug>.toml`. On a corpus that carries any of this, one
`sq repair` can touch every file you just imported.

**No body that carries prose is touched** — a role or skill body with content in it is left as it
is, and a skill you added yourself is never touched, empty or not. A role body left holding prose
is accepted, and `show` prints the prose in place of the rendered definition; a generated-skill
body left holding prose fails `sq check` with a missing seeded view tag error, whose message gives
the steps that restore the rendered definition. Neither is any other item's
body, any sub-entity's body or discussion, any operator item, or any frontmatter field on anything
that is not a role.

Three consequences for an adoption run:

- **Run it on a clean working tree.** `sq repair` cannot separate its changes from yours, so
  commit or stash first and review its diff on its own.
- **It is not only `sq repair`.** `sq adopt`, `sq renumber` and the index rebuild at the end of
  `sq migrate up` rebuild the index the same way and perform the same rewrite. Adopting a folder
  of hand-written squads-native markdown therefore rewrites those files on the first `sq adopt`.
- **Every route announces it.** All four print the same line — `stripped retired regions from
  N item files — review the diff` — and all four name the rewritten items in the reflog:
  `sq repair`, `sq adopt` and `sq migrate up` on their `repair` entry, `sq renumber` on its own,
  where the ids are the post-shift ones because the rebuild that strips runs on the
  already-renamed files. The notice is a count and the reflog names items, so `git diff` is
  still what shows you what moved inside each file.

A squad that carries none of that content is left byte-for-byte alone: no file is written, and a
second run is always a no-op.

## Letting an agent do it

After `sq adopt`, the project's `CLAUDE.md` and the `squads` skill teach the agents the workflow.
Point an agent (e.g. the manager or tech-lead) at the legacy docs and ask it to migrate them
file-by-file using the steps above — it already knows the commands, and `--at` lets it stamp each
item with the date it reads from the source document.

## Notes & caveats

- `--at` sets **both** `created_at` and `updated_at` for a `create`; re-run later commands at later
  dates to advance `updated_at`.
- One timestamp per invocation — run a separate `sq … ` command per historical event.
- The global counter is monotonic: IDs reflect *adoption* order, not historical order. The dates
  (not the ID numbers) carry the timeline.
- A task's parent must be a feature; bugs/reviews attach via `--kind fixes|addresses` (see
  `sq workflow`).
