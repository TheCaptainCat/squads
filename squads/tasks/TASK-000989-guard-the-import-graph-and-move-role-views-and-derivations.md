## Scope

Three steps that change no behaviour and no generated byte (ADR-984, order of work, steps 1
to 3). They record the package import edges as a table, give the roster projection a home
every consumer can import, and move the role derivations that TASK-990 rewrites out of the
992-line `_interactions/__init__.py`. They merge ahead of any behaviour change in FEAT-986.

It is built after TASK-954, FEAT-980 and the bump of the working version to 0.16.0, and
before TASK-990. It changes no bundled file, so nothing in it depends on the version it is
built at; ST2 edits one import line in a released migration runner, which is why it follows
the two tasks that edit `_migrations/`.

Nothing here is adopter-visible: no CHANGELOG entry, no `docs/` change.

## Subtasks, in build order

- **ST1, the import-graph guard.** One `tests/meta` module holding the allowed
  package-to-package edges as a table, seeded from the graph as it is today (REV-956
  finding 16). The next two subtasks change edges, and the guard makes each one a line in a
  diff. The same subtask corrects the three passages of `CLAUDE.md` that the measured graph
  contradicts.
- **ST2, the roster views move to `_roles/`.** `RoleView` and `OperatorView` leave
  `_backends/_base.py`; the two structural protocols that stand in for them are deleted
  (REV-956 finding 2).
- **ST3, the role derivations get a named module.** Role-to-type, role-to-skill, lane
  derivation and the two template-facing helpers leave `_interactions/__init__.py` (the part
  of REV-956 finding 5 that TASK-990 rewrites).

One developer, in this order: ST2 and ST3 both edit `_interactions/__init__.py` and
`_backends/_base.py`, and each one's acceptance is a diff of ST1's table.

## Out of scope

- The rest of REV-956 findings 5 and 6. `_interactions/__init__.py` stays a non-empty init
  (playbook data, skill naming, view-name constants, roster liveness, orphan-guide detection,
  cheatsheet anchoring). No parameter becomes required here; TASK-990 does that.
- `is_dev_slug` and both `DEV` constants are moved or left where they are, never changed.
  TASK-990 deletes them.
- The managed region of `CLAUDE.md` (between the `squads:start` and `squads:end` markers).
  It is regenerated from its template and is not touched here. Only the hand-written part
  above it is edited, and only for the three passages ST1 names.

### ST1 — Record the package import edges in a tests/meta guard

<!-- sq:subtask:ST1:body -->
**Goal.** The package import edges of `src/squads` are a recorded table. A new edge, or an
edge that disappears, is a one-line change in a diff instead of something each change
re-derives. `CLAUDE.md` says what the table shows.

**Approach**

- One new module in `tests/meta`, named for the behaviour it pins. It walks every module
  under `src/squads` with `ast` and reduces each import to an edge between two nodes, where a
  node is the first path component under `squads` (a package such as `_roles`, or a top-level
  module such as `_views`, `_paths`, `_itemfile`).
- Each edge carries its kind: top-level, function-local, or `TYPE_CHECKING`-only. The three
  are recorded separately, because a function-local import is how a cycle is held apart
  today (50 edges in 20 modules, REV-956 finding 16).
- The table is seeded from the measured graph and is compared for **equality**: an edge the
  table does not list fails and names the importing module and line; a row whose edge no
  longer exists fails too. Rows are data, one per line, sorted.
- A second assertion pins the package-level strongly connected component over top-level
  edges as a recorded set of nodes (eight in REV-956 finding 16's measurement: `_backends`,
  `_badges`, `_interactions`, `_overrides`, `_paths`, `_rendering`, `_views`, `_workflow`). A node joining it fails;
  a node leaving it is a row to delete.
- A third assertion records the package inits that hold code, as a set. REV-956 finding 5
  measured five where `CLAUDE.md` names three: `squads/__init__`, `_cli/__init__` and
  `_backends/_claude_code/__init__`, plus `_workflow/__init__` and `_interactions/__init__`.
- The reviewer's measuring script is no longer on disk. What it did: walk every module, put
  each `squads` import into one of three sets (top-level, inside a function, inside
  `if TYPE_CHECKING:`), resolve `from pkg import name` to `pkg.name` when that is a module,
  and reduce both ends to the first component under `squads`. It ignored relative imports
  and dynamic imports, and its `from pkg import name` rule needs its own rows. Rebuild the
  walker from that description and test it as below. `_backends/_registry.py` imports
  backends through `importlib.import_module`; decide how the guard sees that edge and say so
  in the table.

**Correct `CLAUDE.md`** (the hand-written part above the managed region; contributor
documentation, edited directly)

- Work from the file as it stands: it has changed since this subtask was written, and its
  line numbers are not cited here. Three passages, all in "Architecture & layering", are
  brought in line with the measured graph:
  - the layering diagram (`_cli → _services → (index store, backends, rendering)`): it shows
    the edges that exist, or the direction rule the table enforces, whichever stays true;
  - the line "`_models` shared, no internal deps": `_models/_item.py` imports `_clock`,
    which imports `_context`;
  - the sentence listing "the only non-empty inits".
- Keep it short and point at the guard module as the place the edges are recorded. Do not
  copy the table into the file, where it would go stale again.
- Nothing between the `squads:start` and `squads:end` markers changes. Hash that region
  before and after.
- Any other sentence the measurement contradicts is listed in the handoff with its
  evidence, not edited.
- ST2 and ST3 change edges: re-read the three passages against the final tables at the end
  of ST3.

**Tests**

- The walker is tested on synthetic source, as a table of import form by position. Forms:
  `import squads.a.b`, `import squads.a as x`, `from squads.a import b` where `b` is a
  module, the same where `b` is a name, `from squads import _clock as clock`, a relative
  import, a dynamic `importlib.import_module("squads.a")`. Positions: module top level,
  function body, class body, an `if TYPE_CHECKING:` block, a `try`/`except ImportError`
  block. Each row states the edge and kind expected, or that the form is refused loudly.
- Known positives, checked before the seeded table is trusted: `_itemfile -> _roles`,
  `_models -> _clock`, `_views -> _backends`, one function-local edge
  (`_overrides/_service.py` importing `_interactions` inside a function) and one
  `TYPE_CHECKING` edge. A walker that returns none of these is not measuring.
- Invariant: the stated rule "`_backends` does not import `_index`" holds as the absence of
  that row.

**Falsify.** Four breaks, each restored: add an import that creates an unlisted edge (for
example `_models` importing `_services`); delete a row whose edge still exists; add a row for
an edge that does not exist; add a statement to an empty package init. Record the failure
message for each.

**Acceptance**

- The guard passes on the unchanged tree, and its failure message for a new edge names the
  importer, the line and the row to add.
- The three `CLAUDE.md` passages state what the tables record, each checked against the
  edge or the init that shows it, and the managed region's hash is unchanged.
- No source file under `src/` changes in this subtask.

Gates and working rules: the task body.

### ST2 — Move RoleView and OperatorView into _roles

<!-- sq:subtask:ST2:body -->
**Goal.** `RoleView` and `OperatorView`, the roster projection every consumer reads, live
beside `RoleDef`, which they project. `_interactions`, `_views`, `_backends` and `_services`
all import them downward, and no structural stand-in is needed.

**Approach**

- Move both dataclasses, unchanged, from `_backends/_base.py` to a new module in `_roles/`
  (suggested `_roles/_projection.py`; it imports nothing internal).
- Update every importer: `_services/_base.py`, `_views.py`, `_backends/_base.py`,
  `_backends/_claude_code/_backend.py`, `_backends/_agents_md/_backend.py`, and
  `_migrations/_v0_11_to_v0_14.py` (the import line only; a released runner is otherwise
  untouched, and it now takes the run's context, which this move does not change), plus the test files that import either name. No re-export is left in
  `_backends/_base.py`.
- Delete `_RoleGuideBearing` and `_SlugBearing` from `_interactions/__init__.py`.
  `item_skill_role_sections` takes `Iterable[RoleView]`. `example_assignee_slug` keeps its
  mapping arm, because `templates/agents_md/agents_section.md.j2` hands it plain dicts.

**Tests**

- Characterisation table, written before the move: role shape (bundled, bundled with a
  per-slug override that renames it, templated developer, project role declared by a role
  file, a role whose backing definition is gone) by field of the `RoleView` that
  `Service.roster()` returns. The same rows for `Service.operators()` over a live and a
  retired operator.
- Invariant: for the fixed roster of the task body, the rendered `CLAUDE.md` and `AGENTS.md`
  managed regions are byte-identical before and after.
- Run `tests/meta` (the migration-import guard reads the runner whose import line changed).

**Falsify.** Drop `mission` from `ServiceCore._role_view`, record the test that goes red,
restore. Then restore the `_backends._base` import in `_views.py` and record the guard's
failure.

**Acceptance**

- Guard table diff: the `_views -> _backends` edge is gone, and every `-> _roles` edge that
  is new is listed. The handoff quotes the diff.
- `rg "_RoleGuideBearing|_SlugBearing" src tests` finds nothing, checked against a known
  positive on the commit before.
- Tests change by import line only, apart from the characterisation table.

### ST3 — Move the role derivations out of the _interactions init

<!-- sq:subtask:ST3:body -->
**Goal.** Everything that decides what the playbook gives a role sits in one named module, so
TASK-990 rewrites one module instead of a 992-line package init.

**Approach**

- New module inside `_interactions/` (suggested `_interactions/_role_guidance.py`). It stays
  in this package on purpose: the functions need the playbook models and the role types, and
  `_interactions -> _roles` is the direction that already exists. A home in `_roles/` would
  add the reverse edge.
- Move, with bodies unchanged: `is_dev_slug`, the `DEV` constant of
  `_interactions/__init__.py`, `create_lanes`, `laned_types`, `is_lane_exempt`,
  `catalog_default_slug`, `allowed_create_types`, `in_lane_owner`, `item_types_for_role`,
  `skills_for_role`, `item_skill_role_sections` and `example_assignee_slug`. That is lane
  derivation, role-to-type, role-to-skill, and every function in the init that reads
  `is_dev_slug` or `DEV` except `orphaned_playbook_guides`, which stays and imports `DEV`
  from the new module (as `authoring_owner` imports `in_lane_owner`). The second `DEV` in
  `_interactions/_loader.py` is untouched.
- The moved functions fall back to the bundled playbook singleton, which the init defines.
  The new module must not import the package root back at module level. Keep the fallback
  behaviour exactly as it is (TASK-990 deletes it); a function-local read of the accessor is
  acceptable here for that reason.
- Update every importer to the new module: `_services/_base.py`,
  `_services/_config_integrity.py`, `_backends/_base.py`, `_cli/_common.py`, `_cli/_role.py`,
  `_overrides/_service.py` (one top-level and one function-local import),
  `_rendering/_engine.py` (the Jinja filter and global registrations), and the tests that
  import a moved name. The init keeps no re-export.

**Tests**

- Characterisation table, written against the init before the move. Role shapes: bundled
  (`architect`), templated developer (`python-dev`), a project role whose slug ends in
  `-dev` and which `sq dev add` did not create, a project role with another slug, an `op-`
  slug, a slug that names nothing. Functions: `item_types_for_role`, `skills_for_role`,
  `allowed_create_types`, `in_lane_owner`, `is_lane_exempt`, `item_skill_role_sections`,
  `example_assignee_slug`. Documents: the bundled playbook, a playbook override that adds a
  guide with `authors = true`, a workflow override that drops a type the playbook names.
  The rows record today's answers, including the ones TASK-990 changes.
- Invariant: the generated files of the task body's fixed roster are byte-identical before
  and after, and so are the same files for a roster with no developer.

**Falsify.** In the moved module, make `skills_for_role` drop the memory skill, record the
test that goes red, restore. Repeat once for the lane family (`allowed_create_types` returns
an empty set) and once for `item_skill_role_sections` (the developers section always
renders). A family no existing test catches gets its characterisation row first.

**Acceptance**

- Each moved name has one definition, and `_interactions/__init__.py` no longer defines any
  of them (`rg "^def (is_dev_slug|create_lanes|skills_for_role)" src` finds one hit each, in
  the new module).
- Guard table diff quoted in the handoff. Expected: no new package edge.
- Tests change by import line only, apart from the characterisation table.
- The three `CLAUDE.md` passages ST1 corrected still agree with the guard's final tables.
