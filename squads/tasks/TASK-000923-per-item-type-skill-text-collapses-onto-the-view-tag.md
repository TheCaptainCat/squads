## Scope

Collapses US3 (per-item-type skill) and US4 (registered filters) of FEAT-906 onto the
source+template+tag mechanism. **Depends on TASK-922** landing first — it shares the
`_cli/_skill.py`/`ServiceCore.skill_definition_text` seam TASK-922 deliberately left standing
for per-item-type skills; do not start this task's deletions before that one is Done.

### Filters (US4)

- Register `linearize_lifecycle` as a Jinja **filter** (`env.filters[...]`), converting its
  current registration as a global (`env.globals["linearize_lifecycle"]`) — ADR-880's ruling is
  literal that "the sanctioned extension point is a filter registered in
  `_rendering/_engine.py`." Update the one known call site
  (`templates/workflow.md.j2`'s `{{ linearize_lifecycle(spec.machine_for(type)) }}`) to filter
  syntax (`{{ spec.machine_for(type) | linearize_lifecycle }}`) rather than leaving a stray
  global doing the identical job beside the new filter.
- Newly register `_item_skill_role_sections`, `custom_item_skill_commands`, and `label_for` as
  filters, beside it. Each stays exactly the pure function it is today — a function of the spec,
  the playbook, and (for `_item_skill_role_sections`) a caller-supplied roster argument — never
  reimplemented in Jinja, only exposed. `_item_skill_role_sections` currently lives on
  `ServiceCore` (`_services/_base.py:458`); moving a pure function out of a service class so it
  is importable from `_rendering/_engine.py` with no `_services` -> `_rendering` edge is this
  subtask's placement call — confirm the import graph stays acyclic and the direction stays
  downward (verified by the project's own import-graph meta guard).

### The one open design question this task must resolve first (US3)

`_item_skill_definition_text` derives its `type` kwarg from a per-item-type skill item's own
**slug** (`sq-<type>`), never from the skill item's own `item.type` (always the roster type
`skill`). Every existing source kind resolves its target type from `view.source.name` (a static,
spec-declared literal) or `item.type` (the host's own type) — **neither is the per-type skill's
own described type**. And unlike the bundled/milestone case, a project-declared custom type's
`sq-<custom>` skill is generated by exactly the same code as a bundled one
(`_write_item_skills` derives one skill per declared item type, built-in and custom alike, with
no per-type TOML) — so the tag mechanism has to generalize the same way, or a custom type's
per-item-type skill silently stops rendering with `sq check` clean, which is precisely the
failure class this feature exists to eliminate elsewhere.

Investigate and drive both shapes below against the bundled spec AND a synthetic custom-type
override (the same technique TASK-918's playbook agreement-pinning test used) before writing the
rest of this task. Report which one actually works, in the handoff comment, before proceeding:

1. **`WorkflowSpec` synthesizes one `playbook`-sourced view per declared non-roster item type at
   merge/load time** (an entry equivalent to `[views.sq-<type>] source = { kind = "playbook",
   name = "<type>" }`), the same way `_write_item_skills` already synthesizes one skill per type
   with no per-type TOML — never a hand-authored literal block per bundled type in
   `workflow.toml`. Presentation still resolves per view NAME
   (`templates/views/<name>.md.j2` — see `view_template_name`'s docstring and the module-level
   rule in `_views.py`). Confirm whether a single bundled `templates/views/item_skill.md.j2` can
   serve every synthesized name (a template-name indirection, or every synthesized `ViewSpec`
   pointing at one shared template path) without breaking "presentation resolves by the view's
   own declared name" — if it can't, that rule itself is the blocker, and belongs in the report
   below rather than a workaround that quietly special-cases this one family.
2. A mechanism that lets `resolve_source` derive the target type from the skill item's own SLUG
   rather than `view.source.name`/`item.type` — a materially bigger change to
   `_resolve_playbook_source`'s contract that revisits FEAT-903's already-shipped, reviewed
   shape. Fallback only if (1) is unworkable; get the sign-off a shape change to Done, reviewed
   code deserves before touching it.

**If neither shape lands cleanly, this is a finding to report — to me and to the architect — not
a detail to paper over.** ADR-880's argument was that every bespoke read-time render path
collapses onto one declared mechanism; a per-item-type skill that genuinely can't is evidence the
argument was incomplete for this one case, and the honest resolution is a proposed new
`source.kind`, or a scoped, explicitly ruled exception — never a silent hack that happens to
cover only this repo's own bundled types.

### Once the mechanism is settled

- Seed each `sq-<type>` skill's own tag at the write point its body file is first created —
  `_backends/_claude_code/_backend.py::_write_managed_skill`, the same seam TASK-922's
  system-skill seeding touched; extend it, don't re-derive it.
- **Backfill** every existing per-item-type skill body file (this repo's own `sq-task`/`sq-bug`/
  … skills included) the same way TASK-922 backfilled the three system skills — idempotent,
  reported count, never touches a non-empty body.
- Delete `_cli/_skill.py`'s `if system: ... else: ...` branch entirely — `skill_show` reads every
  skill's body generically (`await svc.read_body(it.id)`, tag-expanded for a system-owned body,
  authored content unchanged for a custom one) with no branch. Delete `ServiceCore
  .skill_definition_text` and `_item_skill_definition_text` wholesale — TASK-922 left the three
  named system-skill branches in place deliberately; this task removes what remains, including
  the now-otherwise-dead `SQUADS_SKILL`/`GREETING_SKILL`/`MEMORY_SKILL` dispatch if nothing else
  reads it.
