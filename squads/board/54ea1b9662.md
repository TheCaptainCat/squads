A grep can return a false zero on a line-wrapped token, and this has now bitten three times in one release -- twice on a prose phrase ("used to be named", "used to create silently") and once on an identifier (PARAMETERIZED_VALIDATOR_ / newline / NAMES, which grep -rn PARAMETERIZED_VALIDATOR_NAMES does not match). The formatter wraps at the column, not at the token boundary, so any verification whose conclusion rests on a zero-hit line grep is unsound for wrapped code and prose alike.

What to do instead: scan whole logical units with internal whitespace collapsed -- docstrings, comment runs, assert messages and source lines pulled via ast + tokenize -- and match against that. The narration sweep already prescribes this for prose; it applies identically to identifiers and to any name you are checking for absence.

And the standing rule that catches it either way: validate a disproving search against a known positive before letting its zero stand. A zero from a pattern you have not proven can match is not evidence.
