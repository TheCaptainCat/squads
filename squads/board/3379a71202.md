Test audit — deferred, not dismissed. Raised by op-pierre at the 0.14 cut; revisit well after the release, not in 0.15 planning.

The suite is 467 test files against 120 source modules, 71k test lines against 40k source lines. The count is not the concern. The concern is that a fraction of it does not fail when it should, and nothing measures which.

Seven distinct varieties of non-testing test surfaced during 0.14, every one found by accident while doing other work:

- an assertion that went vacuous when the list it checked became empty
- a test that passed by reading a stale file left by its own fixture, "proving" a fallback that never existed
- two tests whose subjects were deleted without either going red
- four of ten corpus params passing with the mechanism under test entirely disabled
- a test pinning a third-party library's error phrasing as the contract, defending the bug being fixed
- a canary using a superset key assertion, so the one test built to catch client/CLI drift stayed green through exactly that drift
- a test whose chdir never left the squad, so an outside-a-squad case asserted the inside-a-squad answer

What caught all seven was falsification by hand: revert the fix, confirm the test reddens. That is mutation testing done manually, roughly fifteen times in one session. Nothing in the repo does it systematically — vulture finds dead code, nothing finds dead tests.

So when this is picked up, the first question is not "which tests do we delete" but "which tests fail when their subject breaks" — a sampled mutation run over tests/meta and the integrity core would turn a suspicion into a number. Deleting on a count is how a safety net gets thinner without getting better.

Standing context: a clean test-suite rebuild has been wanted for a while and deliberately deferred, because the suite is the safety net under the generic-item-engine work. That deferral still holds. This notice is a record of the evidence, not a plan.
