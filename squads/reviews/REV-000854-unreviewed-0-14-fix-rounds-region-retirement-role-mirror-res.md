### F1 — Retired sub-entity regions go wrong on the next mutation and never converge

<!-- sq:finding:F1:body -->
**driven.** The write path stopped materialising the sub-entity `:head` badge line and the
parent `:summary` roll-up table, and existing files were left carrying both. They do still load,
show and check clean — that half of the acceptance holds and was verified. What was not
considered is what happens when such a file is **mutated**: the frontmatter moves, the regions
do not, and nothing ever reconciles them. The file stops being merely vestigial and becomes
self-contradictory.

`src/squads/_services/_subentities.py:753` is the seam. Every sub-entity mutation now runs
`text = discussion.set_heading(text, kind, sub.local_id, sub.title)` and nothing else against
the body — the `_refresh_head` and `ensure_summary` calls that used to follow it are gone. So a
status change, a reassignment or a story remap rewrites the frontmatter and leaves the rendered
badge line and roll-up row at their pre-mutation values, permanently.

## Repro (driven)

A corpus was generated with the pre-retirement binary (`fd40fe9`) and then driven with HEAD
(`1d03e2a`), each from its own worktree virtualenv:

```
# generated at fd40fe9: FEAT-22 with US1 (Done) and US2 (Todo, assignee qa)
# then, at 1d03e2a:
sq feature 22 story 2 update --status InProgress --assignee devops
sq sync
sq repair
sq check
```

Frontmatter afterwards, via `sq feature 22 show`:

```
US1    Done                  First story
US2    InProgress  devops    Second story
```

The file's own body afterwards, unchanged by any of the three commands above:

```
[sq:summary]
| US1 | Done |  | First story |
| US2 | Todo | qa | Second story |
[sq:summary:end]
...
[sq:story:US2:head]
**Status:** ⚪ Todo
**Assignee:** Mara Tester
[sq:story:US2:head:end]
```

`sq check` reports no issue about it — `src/squads/_services/_validators.py` has no rule that
mentions `summary` or `:head` at all. `sq sync` does not touch it. `sq repair` rebuilds the
index from the frontmatter and does not touch it either. There is no convergence path.

## It also leaks into search (driven)

`sq search "Second story"` on that same corpus returns the stale row as a hit, and the region
label has degraded to `other` because the renderer no longer knows the region:

```
FEAT-22 Parent feature (Draft)
    other: | US1 | Done |  | First story | / | US2 | Todo | qa | Second story |
    story:US2: ### US2 — Second story
```

So the wrong values are not only sitting in the file — they are served back through a read
surface, unlabelled.

## Live blast radius in this repository (driven)

632 files under `squads/` carry a `sq:summary` region; 436 carry a `:head` region. A scan
comparing every roll-up row against the same sub-entity's frontmatter status already finds 11
rows disagreeing — including, pointedly, `TASK-000847`'s own file, whose roll-up says all seven
of its subtasks are `Todo` while the frontmatter says `Done`/`Cancelled`:

```
TASK-000847...md  ST1  frontmatter=Cancelled  roll-up row=Todo
TASK-000847...md  ST3  frontmatter=Done       roll-up row=Todo
...
TASK-000848...md  ST1  frontmatter=Done       roll-up row=Todo
```

That count only grows: every future mutation of any of those 632 files adds to it.

`tests/fixtures/corpus/v0_14/` — the fixture representing what a squad *looks like* at the
target schema — still carries the regions too, so the shipped 0.14 target state includes files
the write path no longer maintains.

## Missing coverage, which is why this got through

The rewritten sub-entity tests all build their fixtures with the **new** write path, so every
one of them asserts the regions are absent. Not one test constructs a file that already carries
them, mutates it, and asserts anything about what the regions then say. That is the entire
untested seam.

## What would close it

Either the write path keeps the regions current while they exist on disk, or `sq check` grows a
rule that reports a materialised region disagreeing with frontmatter, or the strip lands — see
F2, which is the reason the strip as currently planned will not reach this corpus.

### F2 — The planned corpus strip cannot reach a corpus already stamped 0.14

<!-- sq:finding:F2:body -->
**driven.** TASK-847 deferred the corpus-wide strip to a sibling task, and TASK-849 (`Ready`,
unbuilt) scopes it as *"one more deterministic step inside the release's existing 0.11 → 0.14
runner"*, explicitly declining a second registry entry: *"There is no second
`from_schema`/`to_schema` pair, no second runner module, no second `SCHEMA_VERSION` call."*

That plan cannot reach a corpus that is already stamped `0.14`.

The single registry entry for this release (`src/squads/_migrations/_registry.py`, the last
`Migration` record) declares `from_schema="0.11"`, `to_schema="0.14"`. `sq migrate up` runs
nothing once the stamp already matches:

```
$ python -c "import json;print(json.load(open('squads/.squads.json'))['schema_version'])"
0.14
$ sq migrate up
already at schema v0.14; nothing to migrate
```

## Who is in the exposed population

Exactly the squads whose corpus was written by a 0.14-era build *before* the retirement landed —
they carry the regions **and** the 0.14 stamp, so no runner will ever visit them again. That is:

- **this repository**, whose index reads `schema_version: 0.14` and whose 632 region-carrying
  files are the project's own record; and
- any adopter tracking the 0.14 pre-release.

A squad still at 0.11 is fine — it will run the extended runner on its way up. A squad created
by a post-retirement `sq init` is fine — it never had the regions. The gap is precisely the
middle, and this repository sits in it.

## Why this is filed against the shipped work rather than against TASK-849

TASK-847 shipped the write-path retirement *ahead* of the strip, which is a legitimate staging
choice on its own. What makes it a defect rather than a sequencing detail is that the deferred
remedy, as scoped, has no path to the corpus the shipped change stranded. Either TASK-849 needs
a delivery vehicle that is not the 0.11→0.14 runner (a `sq repair`-adjacent sweep, a new schema
step, or a `sq sync` responsibility), or this repository's own 632 files need an explicit
one-time strip that nothing currently owns.

**inferred**, and flagged as such: whether the intended answer is a new schema step or a
non-migration sweep is a call for the architect, not this review. What is driven is that the
currently declared vehicle does not reach the affected corpus.

### F3 — Compiled managed regions contradict themselves under any role override

<!-- sq:finding:F3:body -->
**driven.** TASK-851's acceptance states: *"A project override declared in `.overrides/roles.toml`
reaches the compiled managed regions and the pointers on the next regeneration."* It reaches the
roster section and the pointers. It does not reach the authoring bullets in the same file, which
still print the bundled catalog's title — so one generated document names the same role two
different ways.

## Repro (driven)

```
sq init --default-names --backend claude_code
sq override scaffold --role reviewer
# append to squads/.overrides/roles/reviewer.toml:
#   title = "OVERRIDE-TITLE"
sq sync
grep -n reviewer CLAUDE.md
```

Output:

```
17:- **Paul Reviewer** — OVERRIDE-TITLE (`reviewer`)          <- roster section: override honoured
107:- The **code reviewer** authors **reviews** ...            <- team workflow: bundled title
```

Line 16 of `.claude/agents/reviewer.md` picks up `OVERRIDE-TITLE` as well, so the pointer and
the roster agree with each other and both disagree with line 107.

## Mechanism (read, confirmed against the template)

`src/squads/_rendering/templates/claude/claude_section.md.j2:130-137` builds a `_role_titles`
map from the resolved `roles` view — the right source — and hands it to `authoring_owner`. But
`src/squads/_interactions/__init__.py:790` reaches for the catalog first and only falls back to
that map on failure:

```python
    try:
        return slug, role_by_slug(slug).title
    except RoleNotFoundError:
        if role_titles is not None and slug in role_titles:
            return slug, role_titles[slug]
```

`role_by_slug` (`src/squads/_roles/_catalog.py:215`) is a straight lookup into the module-level
`_BY_SLUG` bundled map. It takes no `squad_dir`, so neither override layer can reach it: not
the per-role `.overrides/roles/<slug>.toml`, and not the whole-document `.overrides/roles.toml`
either. For any slug the bundled catalog knows — which is every bundled role — the live
resolved title is never consulted. The fallback only fires for a role the catalog has never
heard of.

## Scope note, stated honestly

`_interactions/__init__.py` was **not** touched in this range (`git log 958974c..HEAD` on that
path is empty; the `role_titles` parameter arrived in `683ed8b`, well before it). This is
pre-existing. It is filed here because TASK-851 wrote an acceptance clause against it and the
clause does not hold — the resolution stage moved every *other* consumer onto the catalog seam
and left this one behind, and the byte-diff acceptance could not catch it because the baseline
was equally wrong.

## Fix shape

`authoring_owner` should consult the live resolved titles *first* and fall back to the catalog,
or `role_by_slug` should gain the `squad_dir` argument every other resolution path already
takes. The first is the smaller change and matches the rest of the stage's direction.

### F4 — Ambient-reset guard re-derives one syntax shape; five leak shapes evade it

<!-- sq:finding:F4:body -->
**driven.** `tests/meta/test_ambient_render_state_reset_is_exhaustive.py` claims to re-derive
the reset set from source and *"fails if a third ambient value is added there without being
listed"*. It holds for today's tree, and its two plant tests do exercise the real walk. But the
derivation recognises exactly one syntactic shape, and five realistic ways of introducing the
same leak walk straight past it.

## Repro (driven)

Seven candidate modules were planted and run through the guard's own wired walk,
`_reset_target_candidates` — the function the real assertion calls, not a re-implementation:

```
alias_import           -> {}   EVADED
nested_in_try          -> {}   EVADED
nested_in_if           -> {}   EVADED
tuple_target           -> {}   EVADED
factory_call           -> {}   EVADED
bare_cache_no_cvar     -> {}   EVADED
class_attr_cache       -> {'engine/_m.py': {'_leak'}}   DETECTED
```

The shapes, and why each slips through:

- **`alias_import`** — `from contextvars import ContextVar as CV` then `_leak = CV(...)`.
  `_contextvar_names` (`:124`) matches on the *called name* being literally `ContextVar`
  (`_call_target_name` returns `Name.id` or `Attribute.attr`), so any alias defeats it.
- **`nested_in_try` / `nested_in_if`** — the walk is `for node in tree.body` (`:127`), module
  **body statements only**. A `ContextVar` declared inside a module-level `try:` or
  `if sys.version_info ...:` block lives in that statement's own `body` and is never visited.
- **`tuple_target`** — `_a, _b = ContextVar(...), ContextVar(...)`.
  `_module_scope_target_and_value` (`:105`) returns `None` for anything but a single
  `ast.Name` target.
- **`factory_call`** — `_leak = _mk("_leak")` where `_mk` returns a `ContextVar`. The call
  target is `_mk`, not `ContextVar`.
- **`bare_cache_no_cvar`** — a module-level dict keyed by squad dir, in a file with no
  `ContextVar` beside it. This one is excluded **by design**: the guard's own docstring says a
  cache is only a candidate when it shares a file with a leaking `ContextVar`. But the
  companion-cache rule is a *proxy* for "keyed off ambient state", and the property it proxies
  for can exist perfectly well without a `ContextVar` in the same module. This is the shape
  closest to the original bug and the one most likely to recur.

## Severity, argued down rather than up

Low, for two concrete reasons. Today's tree has exactly one module-level mutable cache
(`_env_cache`) and it is correctly listed. And `tests/meta/test_no_unallowlisted_module_level_
mutable_state.py` would independently redden on a new bare cache, forcing an allowlist entry
with a written reason — so the `bare_cache_no_cvar` path is not silent, it just routes the
decision to a human who is answering a different question ("is this CODE?") than the one that
matters here ("is this fixture-primable?").

What is overstated is the guard's own claim of exhaustiveness. It is exhaustive over
`name = ContextVar(...)` at module body scope, and the docstring should say that rather than
"a third ambient value".

## Fix shape

Widen the walk to `ast.walk` rather than `tree.body`, resolve import aliases for `ContextVar`,
and accept tuple targets — each is a few lines against `_contextvar_names` /
`_module_scope_target_and_value`, and the existing plant tests are the right place to pin them.
Whether to widen the cache rule beyond the companion heuristic is a judgment call worth stating
in the docstring either way.
<!-- sq:finding:F4:body:end -->

### F5 — Migrate and sync write different managed regions on an override-carrying squad

<!-- sq:finding:F5:body -->
**driven.** TASK-851 moved every service-side consumer onto the resolver and explicitly, with a
stated reason, left the migration runner's local roster projection reading the `extra` mirror:
*"Not in scope, and named so it is not helpfully added."* The reason given (a `Service` call
from a runner is a real import cycle) is correct and I am not disputing it. What is not stated
anywhere is the consequence: the two paths now compile the same managed files from different
inputs, so `sq migrate up` and `sq sync` write **different** `CLAUDE.md` content on the same
squad.

`src/squads/_migrations/_v0_11_to_v0_14.py:152-160` builds its `RoleView` list off
`it.extra.get(X.TITLE, ...)` / `it.extra.get(X.RESPONSIBILITIES, ())`, and then hands that list
to the backend's `write_managed` — the same method `sync` calls with the resolved list.

## Repro (driven)

A squad with a project role override the mirror has not caught up with — i.e. the state a
mid-upgrade squad is actually in:

```
sq init --default-names --backend claude_code
sq override scaffold --role reviewer
# append: title = "OVERRIDE-TITLE"
```

Isolated probe, calling the runner's own projection beside the service's, same squad, same
moment:

### F8 — PERMITTED_EXTRA_SKEW outlived the writer that justified it
