## Context

Claude Code is the first agent harness squads drives, but it was never meant to be the only one. The
design question was whether to write Claude Code's file conventions directly into the core, or to put
an abstraction between the core and any one harness. We chose the abstraction, and we made a second,
related call: the harness-specific files squads writes into `.claude/` are **pointers**, not content.

The reasoning: tying the core to one harness's directory layout would make a second backend a rewrite,
not an addition. And duplicating real role/skill definitions into `.claude/` would create two copies
that drift, and would scatter durable content into a tool-owned tree that squads regenerates. Keeping
the real content in one place (the squad folder) and treating `.claude/` as a regenerated routing
layer keeps a single source for each definition and keeps the core harness-agnostic.

## Decision

**Backends are pluggable behind the `AgentBackend` ABC, and `.claude/` files are thin pointers.** The
ABC's abstract surface is seven methods, named neutrally (ADR-133): the six IO methods
`ensure_scaffold`, `write_managed`, `generate_role_entry`, `generate_skill_entry`,
`remove_artifacts` and `candidate_orphans` are `async def` (ADR-153), and the read-only
`managed_paths` probe that `sq check` uses is sync (ADR-141). Backends are looked up by name in a
literal table in `_backends/_registry.py`, with no registration side effect (ADR-1128); a new
backend is a row there. **Nothing outside a backend reaches into `.claude/`** — the core goes
through the ABC.

Everything the backend writes into `.claude/` routes to real content under the squad folder. A role
or skill pointer carries only what the host must read before an agent can run — its identity, the
text the host selects it by, and the constraints squads imposes on the session — and names the `sq`
commands that fetch the rest (`sq role <slug> show`, `sq skill <slug> show`), never a local path
(ADR-781). `CLAUDE.md`'s managed section (between its `squads` start/end markers) is regenerated from
the roster and workflow. The real role definitions and skill bodies live under `squads/agents/`;
`.claude/` holds only the pointers plus tool-owned config (`settings.json`, merged on write and never
clobbered).

## Consequences

- **A second harness is an additive backend**, not a core change: implement the ABC, add its row to
  the registry table, done. No command may special-case Claude Code outside its backend; the
  `agents_md` backend is the second one built this way.
- **No durable content lives in `.claude/`.** Role and skill content has exactly one home (the squad
  folder); the `.claude/` files are regenerated by `sq sync` and are safe to delete and rebuild.
- **`settings.json` is merged, never clobbered** — the backend unions permission entries into an
  existing file rather than overwriting the operator's keys.
- **The pointer indirection costs a hop**: reading a role means running the command the pointer
  names to get the real definition. That is the deliberate price of single-sourcing the content and
  keeping the core harness-agnostic.

## Provenance

Recorded retroactively. This decision predates squads tracking itself and lived only in `CLAUDE.md`
(invariants 5 and 6) and `docs/internals.md` (§7). It is documented here as a decision already **in
force**, not newly debated in-tool.
