## Context

A squads skill pointer is a redirect: its body tells the agent to run `sq skill <slug> show`, and the
agent decides whether to. Over 539 subagent runs in this repository, 62% ran `sq role <slug> show`,
18% opened a per-type skill and 5% opened `squads` (read: FEAT-1290, product-owner's measurement).
The playbook guidance lives only in the per-type `sq-<type>` skills, so most agents never read it,
and a per-type skill is 70-75% text addressed to other roles.

Claude Code renders a `` !`command` `` line in a skill body when the skill loads, and the agent
receives the output in its first message with no tool call. Facts this decision rests on, each
labelled: **driven** (seen in a host transcript in a throwaway project, Claude Code 2.1.318),
**read** (from the feature's recorded measurements or the code), **inferred**.

- A preloaded skill's `!` line renders into the subagent's first message (driven). A
  `user-invocable: false` skill still preloads (driven; this closes ADR-983's inferred claim).
- An agent file's body is not rendered (read). A preloaded skill gets an empty `$ARGUMENTS` and
  cannot tell which agent loaded it (read).
- A render whose command exits non-zero, or that the permission check rejects, aborts the whole
  spawn (read, and driven for the rejection: an unapproved render aborted the Agent call).
- In a workspace the host has not trusted, the project's `settings.json` allow rules are ignored;
  a skill's own `allowed-tools` entry still lets its render pass (driven).
- `sq … || echo '…'` passes the permission check when the skill declares only the `sq` command:
  the `echo` half needs no grant (driven). When `sq` exits 1, the agent receives sq's stdout, its
  stderr and the echo line, and the spawn goes ahead; when `sq` is not on the PATH it receives
  `(eval):1: command not found: sq` and the echo line, and the spawn goes ahead (driven). The
  command runs in the user's shell with the host process's environment: a PATH set on the host
  process was honoured (driven).
- Render output is not re-expanded: a `` !`…` `` line inside sq's output reaches the agent as text
  and does not run (driven).
- A YAML comment in a pointer's frontmatter does not reach the agent and does not disturb the
  frontmatter; an HTML comment in the body does reach it (driven, for a skill; for an agent file
  the spawn and preload worked with a frontmatter comment, and that the comment is not in the
  system prompt is inferred from the same parser).
- A model-invoked skill receives the Skill tool's `args` as `$ARGUMENTS`, substituted as plain
  text before the shell parses the line; quoting in the skill does not contain it, since a quote
  in the argument closes it (driven). Whatever the substituted line runs is still checked: an
  injected `touch` was refused and the skill failed, an injected `echo` ran (driven).
- A model-invoked skill with a `!` line needs the `Skill(<name>)` permission; without it the
  invocation fails in a non-interactive session (driven) and prompts in an interactive one
  (inferred). A skill with no `!` line needed none (driven).
- `sq skill <slug> show --raw` prints the metadata panel and wraps at 80 columns (read).
  `sq memory <slug> list` and `sq board list` print ANSI under `FORCE_COLOR=3` and wrap at 80
  columns (read, on the released tool). `sq board list` prints each notice's full content.
- A skill whose `allowed-tools` names three commands, each used by its own `!` line, preloaded
  into a subagent in an untrusted workspace, rendered all three lines when the grant was a YAML
  list, a comma-separated string or a space-separated string; with one of the three left out of
  the grant, the spawn failed on that line (driven).

Board notice 22 governs every mechanism below: each one is an `sq` client call and reads nothing
local, so it works the same against a hosted squad.

## Decision

### 1. A skill pointer renders its body through never-failing commands

The Claude Code skill pointer is, for a skill item `<slug>`:

```
---
# Generated by squads and regenerated by `sq sync`: hand-edits here are overwritten.
name: <slug>
description: "<description>"
user-invocable: false
allowed-tools: Bash(sq skill <slug> show --raw --no-header)
---
!`sq skill <slug> show --raw --no-header || echo 'squads could not render the <slug> skill; run: sq skill <slug> show'`
```

`user-invocable: false` appears exactly as ADR-983 resolves it. Nothing else is in the file. The
role skill (§2) is the one pointer with more than one `!` line.

- **The command.** Each `!` line is one `sq` command, then `||`, then one `echo` of a single-quoted
  ASCII line naming the command to run by hand. The quoted text holds no `$`, backtick, `!`, glob
  character or brace, so bash and zsh parse it alike; slugs are `[a-z0-9-]` and need no quoting.
  Each line always exits 0: a failing or missing `sq` falls through to its own echo, and a line
  that fails leaves the pointer's other lines unaffected.
- **The grant.** The pointer declares `allowed-tools` naming exactly its own `sq` commands and
  nothing wider. The project's `Bash(sq:*)` rule also covers it in a trusted workspace; the
  pointer's own entry is what makes the first run in a fresh clone work.
- **Raw output.** `--raw` on every `show` (item, skill, role, operator) prints plain markdown: no
  panel, no ANSI, no Rich markup, no wrapping, no emoji badge glyphs, whatever `FORCE_COLOR`,
  `NO_COLOR`, `TERM` or the tty say. `--full` and `--comments` render raw too, sub-entity state as
  plain text. An item prints the `# <id> — <title>` heading, a blank line, the header, a blank
  line, then the body. The header is the rows the normal `show` panel prints, in its order and
  with its labels, one `- **<label>:** <value>` bullet per row. For an item the heading carries
  the panel's id and title rows, so the list starts after them and adds `- **type:** <type>`.
  A role, skill or operator `show` prints no heading under `--raw`, since its body opens with its
  own; its list keeps the panel's unlabelled name row as a plain first bullet. A badge prints its
  value without a glyph, and a ref prints as `<id> (<kind>)`. The session rows are left out. One
  function per show builds the rows, and both the panel and `--raw` print them, so the two cannot
  drift; it replaces the hand-written `_raw_metadata`. `--no-header`, valid only with `--raw`,
  drops the heading and the header and prints the body alone, every view tag expanded; without
  `--raw` it is refused with one line.
- **No `frontmatter` field.** The show DTOs carry no copy of the stored frontmatter, and
  `--json` prints none: the header is built from the fields the DTO already carries.
- **Raw lists.** `sq memory <slug> list --raw` and `sq board list --raw` follow the same contract:
  plain markdown, no ANSI, no wrapping, nothing on stdout unless the whole list was read. Memory
  prints one bullet per entry, its slug and summary. The board prints one numbered item per
  notice with its full content, author, timestamp and expiry: a notice is a team rule, and a
  one-line summary would send the agent to another command for each. Raw output writes nothing to stdout
  unless the whole render succeeded; on failure it exits non-zero with sq's one-line error on
  stderr, which the agent receives above the echo line.
- **Partial failure stays inside the text.** A view that cannot read its source renders one line
  saying so and naming the command, and the render still exits 0. Only a failure to resolve the
  item, the squad or the schema fails the command.
- **Invariant 7.** The regenerated-by-`sq sync` statement moves to a YAML comment on the
  frontmatter's first line, in every pointer squads writes, agent pointers included. Whoever
  opens the file reads it; the agent does not receive it as an instruction. The guidance lines
  ("Load and follow…", "Track related work…", "This pointer file itself is regenerated…") are
  dropped. An HTML comment is not used: it reaches the agent.
- **Drift.** `sq check` compares each pointer with a fresh render as before (ADR-781 §2c); the
  render now includes the `allowed-tools` line and the command lines.

### 2. One role skill per role, a projection of the role

- **Name.** `sq-role-<role slug>`. One per live role, written by `sq sync` as a pointer in
  `.claude/skills/sq-role-<slug>/SKILL.md`, always `user-invocable: false`, model invocation left
  on (preloading draws from it). The role's agent pointer preloads it first in its `skills` list.
- **No skill item.** The role skill is projected from the role item like the agent pointer: there
  is no `SKILL` item for it, nothing to seed, and no stored operator-invocable choice.
- **What it renders, in order.** Three `!` lines, each with its own `|| echo` fallback (§1):
  1. `sq role <slug> show --raw --no-header`: the role's body;
  2. `sq memory <slug> list --raw`: the role's memory index;
  3. `sq board list --raw`: the current board notices, content included.

  Its `allowed-tools` names exactly those three commands, written as a YAML list, one
  `Bash(<command>)` entry per line. A failing line leaves one echo line in
  its place, and the other two still render.
- **The role body.** Beside the adopter's text and the `role_definition` tag (mission,
  responsibilities, working agreements), the role body carries one view, `role_playbook`, seeded
  after `role_definition`: for each item type in the role's playbook, in playbook order (the list
  `item_types_for_role` gives), the type's overview, its lifecycle line, and this role's own
  Enter, Do, Hand off and Watch for section, with live-roster substitution as today. No other
  role's section. A role whose playbook names no type renders nothing here. `sq role <slug> show`
  prints the role definition and its playbook, never memory or board.
- **The adopter's text.** It lives in the role's body, beside the tags, written with
  `sq role <slug> body` as role prose is today; sync never writes a role body. The existing
  view-tag engine places the tags and lets a squad disable one per role. There is one surface per
  agent for a squad's own text, and it already exists.
- **Role definition text.** `role_definition.md.j2` loses the line sending the agent to its
  `sq-<type>` skill and the "Live with the operator" instruction to follow `greeting`, since the
  main session has run `sq-greeting` before it reads its role (§4); it names no command for
  reading the agent's own role, and its references to the `squads` skill name `sq-how-to`.
- **Lifecycle.** Activating or adding a role writes its role skill pointer with its agent pointer;
  retiring removes both (`remove_artifacts`); reactivating writes them again. Role slugs are
  permanent, so a rename changes only the full name or title, and the description re-renders.
  `managed_entry_paths` declares the role skill pointer of every live role, and `candidate_orphans`
  reports a `.claude/skills/sq-role-<slug>/` whose role is not live.
- **Collisions.** `sq skill add` refuses a slug `sq-role-<s>` when `<s>` is a role item's slug,
  any status; `sq role add` and `sq role activate` refuse a role whose `sq-role-<slug>` is an
  existing skill item.
- **Backfill.** `sq repair`'s body-tag sweep places the `role_playbook` tag on a role body that
  lacks it entirely, as it does for `role_definition`; a tag the squad disabled is present and left alone.

### 3. The agent pointer

The agent pointer keeps identity, the host-consumed frontmatter of ADR-781 §2a, and the startup
commands nothing renders: `sq mine <slug>` and `sq inbox <slug>`. The definition command and the
memory and board commands leave it, since its preloaded role skill renders all three.
`_STARTUP_COMMAND_TEMPLATES` holds those two. The preload list is `sq-role-<slug>`, `sq-how-to`,
`sq-memory`. `sq-greeting` is in no agent's list.

### 4. `sq-greeting` states the main session's start

- **The managed `CLAUDE.md` section only directs the session to `sq-greeting`.** One mandatory
  instruction: before its first reply, the main session invokes `sq-greeting` and completes
  every step it gives; a subagent never does. The section's "Impersonation on greeting" and
  "Start of a run" parts, and the greeting paragraph under "Operators", leave it: their content
  is in `sq-greeting`'s body. The roster, operators, working language, orchestration loop, team
  workflow and working-with-squads parts stay; the orchestration loop names `sq-how-to`.
- **The pointer.** The §1 pointer, with no argument:
  `` !`sq skill sq-greeting show --raw --no-header || echo 'squads could not render the sq-greeting skill; run: sq skill sq-greeting show'` ``.
  Subagents never load it: it is in no preload list, and its description says it is for the
  main session.
- **What the body states.** The startup sequence as numbered, imperative steps, each one
  mandatory and in this order, before the first reply:
  1. Identify the operator (the logged-in user or `git config user.name`, checked against
     `sq list -t operator --all`; register only on a yes; ask when unsure, never guess).
  2. Adopt the role: the agent the operator greets by name or function, matched to a live role's
     slug; otherwise the squad's default role, which the body names (full name and slug,
     resolved at render by the `greeting_skill` view; no default renders one line naming
     `sq role set-default`). A greeting that matches no live role means asking, not guessing. A
     human introducing themselves is the operator, not a role to adopt.
  3. Read the role: run `sq role <slug> show --raw --no-header`.
  4. Run `sq mine <slug>`.
  5. Run `sq inbox <slug>`.
  6. Run `sq board list --raw`.
  7. Run `sq memory <slug> list --raw`, then `sq memory <slug> show <entry>` for each entry the request
     touches.
  8. Greet, as the body's tone guidance says.
- **Not rendered.** The steps are text; the render runs none of them. `sq-greeting`'s render
  reads only its own body and the default role, so it is the same for every session of a squad.
- **Plain commands.** The steps are tool calls the session runs, not render lines. Steps 3, 6
  and 7 use `--raw`, so the session reads the same plain text a subagent's role skill renders and
  no ANSI reaches the transcript on a host that forces colour; `sq mine` and `sq inbox` have no
  `--raw` and run as they are.
- **Each step is its own command.** The role read prints the definition and the playbook only
  (§2), so steps 3, 6 and 7 each print something no other step does, and nothing repeats.
- **Why a command reads the role.** Step 3 runs `sq role <slug> show --raw --no-header` rather
  than loading `sq-role-<slug>` with the Skill tool. That skill also renders the memory index and
  the board, which steps 6 and 7 run. A model-invoked skill with a `!` line needs a `Skill(<name>)` allow rule (driven), so the
  skill route needs one rule per role, rewritten as roles come and go, or a wildcard rule whose
  behaviour is not checked; the command is already covered by `Bash(sq:*)`. The command also
  works on a host that loads no skill.
- **Permission.** The Claude Code backend adds `Skill(sq-greeting)` and `Skill(sq-how-to)` to the
  allow rules it merges into `settings.json`, beside `Bash(sq:*)`: the main session invokes both
  by model and both carry a `!` line, so without the rule each fails in a non-interactive session
  and prompts in an interactive one.

### 5. The base skills: names, and what stays in them

- **Names.** Every skill squads ships is prefixed `sq-`: `sq-how-to` (the former `squads`),
  `sq-greeting` (the former `greeting`), `sq-memory`, and the role skills `sq-role-<slug>`. The
  view names `squads_skill` and `greeting_skill` are unchanged.
- **What stays.** A section stays in `sq-how-to` only when every agent needs it on every run and
  no other startup text carries it: the role skill, the managed `CLAUDE.md` section,
  `sq-greeting` or `sq-memory`. Everything else becomes a topic of `sq docs`, and `sq-how-to` ends
  with one line per moved topic: its name and when to read it. The same rule trims `sq-memory`
  and `sq-greeting`. No delivered text tells an agent to open an `sq-<type>` skill or to run
  `sq role <slug> show` for its own role; `sq-greeting`'s step 3 is the main session's only read
  of its role.

### 6. The migration and `sq init`

- **Where.** The unreleased 0.19 to 0.20 runner, not a new schema step (board notice 17).
- **Scan first, write nothing on refusal.** The runner plans over every per-type skill item (a
  system skill outside the three always-on ones, a dropped type's stale skill included), every
  skill item named `sq-role-<s>` for a role `<s>`, and every skill item named `sq-greeting` or
  `sq-how-to`. It refuses the whole run, listing each skill and what it holds, when:
  - a per-type skill carries prose in its `sq:body` beyond its view tag, a discussion comment,
    or a ref from another item;
  - an `sq-role-<s>` skill item exists;
  - a project skill already holds `sq-greeting` or `sq-how-to`.
- **Then.** It renames the `greeting` system skill to `sq-greeting` and `squads` to `sq-how-to`
  (slug and file name; the item ID, and refs to it, are unchanged), removes each per-type skill
  item, places the `role_playbook` tag of §2 on every role body, and the run ends with the backend refresh
  `sq sync` performs. That refresh removes the per-type pointers and the `greeting` and `squads`
  pointers from `.claude/skills/`, writes the `sq-greeting`, `sq-how-to` and role skill pointers,
  rewrites every agent pointer's preload list, the managed `CLAUDE.md` section and the
  `settings.json` allow rules. Pointers are regenerated, never migrated (ADR-781 §6).
- **Manual step.** Move each listed skill's content first: prose into the role body of the role
  it addressed, into a project skill, or into the playbook override; re-point refs. Rename a
  project skill holding `sq-greeting` or `sq-how-to`. A stored `operator_invocable` choice on a
  retired skill is not carried over. A squad's own prose naming `greeting` or `squads` is not
  rewritten. Commit `.claude/` after the run.
- **`sq init`** creates the `sq-how-to`, `sq-greeting` and `sq-memory` skill items, seeds every
  role body with the `role_definition` and `role_playbook` tags, writes the agent pointers, the three skill pointers and one role
  skill pointer per activated role, and no per-type skill.

### 7. The AGENTS.md backend

AGENTS.md cannot run a command at load (ADR-781 §5), so it materialises. Its "Role definitions"
section compiles each live role's body as `sq role <slug> show --raw --no-header` prints it, so
each role gets the same definition, playbook sections and squad prose as the Claude Code role
skill. The memory index and the board are not compiled, since a committed file holding them would
be stale on the next write.

AGENTS.md has no skill to direct a session to, so its managed section keeps the startup sequence
inline: its "Start of a run" part states the steps of `sq-greeting`'s body (§4), with the same
commands (`sq role <slug> show --raw --no-header`, `sq mine`, `sq inbox`, `sq board list --raw`,
`sq memory <slug> list --raw`), from one template partial both render, so the two hosts state one
sequence.

### 8. The measurement

For each role and for the main session, on this repository's squad, at the commit before the
change and the commit after, read from the host transcript (the subagent's or session's first
messages, the method used for the facts above), not from the model's report:

- the agent pointer body (the system prompt squads contributes), in characters;
- each preloaded or invoked skill as delivered: the pointer text before, the rendered text after,
  the role skill's three lines summed, echo lines included where a command failed;
- the total delivered at startup;
- the effective total: the delivered text plus the output of every command the pointer or the
  `sq-greeting` body names, since that is what an agent following it receives.

Recorded on FEAT-1290 as one table. No budget applies.

- Every skill squads ships is prefixed `sq-`: `sq-how-to`, `sq-greeting`, `sq-role-<slug>` (§2,

  name (§6).

- The `frontmatter` field leaves the show DTOs and `--json` (§1).
- Every pointer's `!` line and grant use `sq skill <slug> show --raw --no-header` (§1).
- The role body carries one view beside `role_definition`, `role_playbook`; `role_memory` and
  `board_notices` are dropped, and `sq-role-<slug>` renders three `!` lines: the role, the memory
  index and the board (§2).
- `sq-greeting` takes no argument and renders only its own text; its body states the main
  session's startup as mandatory steps the session runs, the role read with
  `sq role <slug> show --raw --no-header` and memory and board as their own steps (§4).
- The managed `CLAUDE.md` section only directs the session to `sq-greeting`; the impersonation
  and start-of-run text moves into its body, and AGENTS.md keeps the same steps inline (§4, §7).
- The `Skill(...)` allow rules are `Skill(sq-greeting)` and `Skill(sq-how-to)` (§4).
- Under `--raw` an item's `# <id> — <title>` heading comes first, then the header list with a
  `type` row, and `--no-header` drops both; a role, skill or operator prints no heading, since its
  body opens with its own, and its list opens with the name row as a plain bullet (§1).
- `sq memory <slug> list` and `sq board list` gain `--raw` under the same contract, the board
  printing each notice's content; the role skill's lines and `sq-greeting`'s steps 6 and 7 use it
  (§1, §2, §4).
- The three-command grant is written as a YAML list; the list, comma and space forms all passed
  on the host (§2).
- The other points stand as recommended: the role skill is a projection of the role, and a
  subagent's queue stays two named commands.

## Decisions narrowed

- **ADR-781** §2 (a skill pointer renders its definition instead of naming it; the agent pointer
  names only `sq mine` and `sq inbox`), §2a (the skill pointer's contents grow by the
  `allowed-tools` grant and the render lines; the role skill pointer joins the table), §3 (the
  startup set shrinks to the two queue commands) and §5 (AGENTS.md compiles each role's body).
  Invariant 5 holds as written: the pointer carries the command that fetches the rest, run by
  the host at load.
- **ADR-983** §2: the per-type family and its shared default retire. Role skills carry no stored
  choice and are always non-invocable.

Each is narrowed in place with a dated note and linked related (board notice 6); none is
superseded. **ADR-427** stays linked related but is not narrowed: its §2 names the `--raw`
dossier without fixing its shape, and the dossier keeps its heading then bold-key metadata
bullets; a dated note there says so.

## Consequences

- Every agent starts with its definition, its playbook sections, its memory index and the
  board, with no tool call. A skill renders on every load, so a stale pointer can only go stale in
  its frontmatter.
- An agent whose `sq` fails still starts, with one line per failed command telling it what to
  run.
- `sq role <slug> show` grows by the role's playbook sections, never by memory or board.
- The `--raw` metadata bullets' field set follows the panel's rows (type, summary and file join;
  badges lose their glyph); an item's dossier keeps its heading-then-bullets shape. The VS Code
  preview's split is unchanged except that it accepts a label with a space in it.
- `show --json` loses the `frontmatter` key.
- `sq memory list` and `sq board list` gain `--raw`.
- The `item_skill` view, the per-type writer, `ITEM_SKILL_OPERATOR_INVOCABLE` and the
  `custom_item_skill_*` helpers retire.
- An adopter who wrote in a per-type skill must move that text before `sq migrate up` completes,
  and one whose own prose names `greeting` or `squads` updates it by hand.
- The main session's startup is commands it runs, not text it receives: a skipped step shows in
  the transcript, and the managed `CLAUDE.md` section carries no startup text of its own.
- Startup text grows; no budget applies until the measurement is read.

## Alternatives rejected

- **Telling the agent to load a skill.** The measured uptake is the problem this solves.
- **A role skill as its own `SKILL` item.** A second place for a squad's per-agent text beside the
  role body, both rendered into the same skill, and a stored item per role that holds nothing a
  role does not.
- **Rendering in the agent file.** The host does not render its body.
- **An exit-0 guarantee inside `sq` alone.** A missing `sq` exits from the shell, not from `sq`.
- **An HTML comment for invariant 7.** It reaches the agent.
- **`sq-greeting` taking the adopted slug and rendering the role and the queue.** The render
  would depend on an argument the host substitutes into the shell line unquoted, and the
  session's startup is steps it runs, each visible in the transcript, not text delivered once.
- **Loading `sq-role-<slug>` in the main session.** It needs a `Skill(<name>)` rule per role, or
  an unchecked wildcard, and it renders the memory and board that steps 6 and 7 run, where one
  command already covered by `Bash(sq:*)` reads the role alone.
- **A YAML front-matter header.** It printed every stored key rather than a chosen set, and
  the `frontmatter` field it read from sent the whole frontmatter in every `--json`.
- **A separate `--body` flag.** `--raw` already means plain output; `--raw --no-header` gives the
  body alone without a second flag that overlaps it.
- **`--raw=no-header`.** The Typer in this repository errors on a bare `--raw` declared with a
  `flag_value`, and takes `--raw --full` as `--raw` with the value `--full` (driven in a throwaway Typer script).
- **Memory and board as views in the role body.** `sq role <slug> show` would print them to a
  person reading a role, and the main session's read of its role would repeat its own memory and
  board steps.
- **A session-start hook.** It runs before the operator's first message, so it cannot know which
  agent is greeted, and it writes into user-owned `settings.json`.
